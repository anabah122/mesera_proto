# Устройство

Как собран mesera и где что лежит. Про причины решений — [DECISIONS.md](DECISIONS.md),
про формат кадров — [docs/protocol.html](docs/protocol.html).

## Общая картина

Мессенджер из двух половин. Сервер на Python держит журналы и раздаёт транзакции,
клиент в браузере хранит копию журналов и рисует по ней экран.

```
БРАУЗЕР                                СЕРВЕР
                                       
/  index.html + auth.js  ──HTTP──▶  main.py       /api/register
                                     │             /api/login
                                     ▼
                                    users.py  ──▶  db.py  ──▶  SQLite
                                                    ▲
/chat  chat.html + app.js            main.py        │
   │                                  │  /ws        │
   ├─ connection.js ═══WebSocket═══▶ session.py ────┤
   │                                  │             │
   ├─ store.js                        ▼             │
   │     │                          hub.py  ──▶  другие вкладки
   └─ storage.js ──▶ IndexedDB      dialogs.py  (права доступа)
```

Две страницы разделены намеренно: на странице входа нет ни сокета, ни локальной базы,
на странице чата нет формы входа. Сломаться при загрузке на `/` попросту нечему.

## Сквозной путь сообщения

Полезно один раз проследить целиком — дальше каждый узел понятнее.

1. Человек жмёт «Отправить». [`app.js`](frontend/app.js) зовёт `conn.send(doc, 'msg.send', {text})`.
2. [`connection.js`](frontend/connection.js) заводит `txid`, кладёт транзакцию
   в *неподтверждённые* и шлёт кадр `TX`. На экране сообщение появляется сразу,
   с пометкой «отправка…».
3. [`session.py`](backend/session.py) проверяет права через
   [`dialogs.py`](backend/dialogs.py) и зовёт `db.append()`.
4. [`db.py`](backend/db.py) в одной SQL-транзакции выдаёт следующий `idx`
   и вставляет запись.
5. Автору уходит `ACK` с номером, собеседнику и другим вкладкам — `EVT`
   через [`hub.py`](backend/hub.py).
6. [`store.js`](frontend/store.js) на `ACK` переносит транзакцию
   из неподтверждённых в подтверждённые, пишет в IndexedDB и перерисовывает экран.

Ключевое: клиент никогда не пишет в свой журнал сам. Запись появляется там,
только вернувшись с сервера с присвоенным номером.

# Сервер

Python 3.13, FastAPI поверх uvicorn, SQLite. Внешних зависимостей две:
`fastapi` и `uvicorn[standard]`, обе с зафиксированными версиями
в [`requirements.txt`](backend/requirements.txt).

## Точка входа — [`main.py`](backend/main.py)

Собирает приложение и держит три общих объекта: `db`, `users`, `hub`.

**FastAPI** — веб-фреймворк на ASGI. Даёт маршрутизацию, разбор JSON и проверку
входных данных через **Pydantic**: класс `Credentials` описывает тело запроса,
и запрос без нужных полей отсекается до попадания в код.

**uvicorn** — ASGI-сервер, который это исполняет. Модификатор `[standard]`
подтягивает `websockets` и `uvloop`; без него WebSocket работать не будет.

Маршруты:

| Путь | Что делает |
|---|---|
| `POST /api/register` | заводит человека, отдаёт токен, рассылает `user.add` |
| `POST /api/login` | проверяет пароль, отдаёт новый токен |
| `GET /` | страница входа |
| `GET /chat` | страница чата |
| `WS /ws` | всё остальное |
| `/*` | статика через `StaticFiles` |

Страницы отдаются с `cache-control: no-cache`. Иначе браузер держит старую
разметку и не видит обновлённых ссылок на скрипты — на этом легко потерять час,
правя код, который в браузер не доезжает.

Цикл сокета читает кадр как текст и разбирает JSON сам, а не через
`receive_json()`. Так кривой кадр отвечает `NACK` вместо разрыва соединения.

Путь к базе берётся из `MESERA_DB`: в контейнере это том, локально — файл рядом с кодом.

## Журналы — [`db.py`](backend/db.py)

Хранилище документов поверх **SQLite** (модуль `sqlite3` из стандартной библиотеки,
без ORM).

Документ — логическая единица со своим журналом. Записи лежат построчно в таблице
`entries` с составным ключом `(doc, idx)`. Добавление записи не переписывает документ
целиком, поэтому размер журнала не влияет на стоимость операции.

Номера выдаёт отдельная таблица `doc_head` — одним `UPDATE ... RETURNING`,
без сканирования журнала. Выдача номера и вставка идут в одной транзакции,
поэтому параллельные вызовы не могут получить одинаковый `idx`.

Повторная отправки той же транзакции возвращает исходную запись: `txid` уникален
в пределах документа (`UNIQUE INDEX entries_txid`). Это спасает при переподключении,
когда клиент досылает неподтверждённое.

**Про блокировку.** Соединение одно на всё приложение и делится между потоками —
синхронные обработчики FastAPI выполняются в пуле. `sqlite3` такие вызовы
не сериализует, курсоры затирают друг друга. Поэтому каждый доступ идёт
под общим `threading.Lock`. Без него параллельная запись роняет
`InterfaceError` и теряет номера — это ловится
[`test_db.py`](tests/test_db.py) на двадцати потоках.

Режим журнала — WAL: чтение не блокирует запись.

## Пользователи — [`users.py`](backend/users.py)

Пароль хранится как **scrypt**-хэш (`hashlib.scrypt`, стандартная библиотека)
со своей солью на каждого. Параметры `N=2^14, r=8, p=1` заданы в модуле.
Scrypt требователен к памяти, что делает перебор на видеокартах дорогим.

Сравнение идёт через `hmac.compare_digest` — постоянное время, без утечки
по длине совпадения. Когда пользователя нет, хэш всё равно считается
от фиктивной соли: иначе по времени ответа можно было бы перебирать логины.
Текст ошибки одинаков для неверного пароля и несуществующего логина.

Токен сессии — `secrets.token_urlsafe(24)`, лежит в таблице `sessions`.
На пользователя их сколько угодно: каждая вкладка получает свой,
и они не вытесняют друг друга.

`log_add()` кладёт появление человека в журнал состава. `txid` детерминирован
(`user.add:<id>`), поэтому повторный вызов не заводит вторую запись.
`backfill()` при старте достраивает записи для тех, кто был заведён
до появления журнала.

## Права — [`dialogs.py`](backend/dialogs.py)

Идентификатор диалога собран из двух идентификаторов, отсортированных
лексикографически: `d:u_aaa:u_bbb`. Пара всегда даёт один и тот же результат,
кто бы ни писал первым, поэтому отдельной записи о создании диалога не нужно —
первая транзакция и есть его начало.

Два предиката решают всё:

- `can_read` — состав системы виден всем, диалог только его паре;
- `can_write` — в журнал состава пишет только сервер, диалог только его паре.

Это единственная преграда между чужой перепиской и клиентом, поэтому
[`test_dialogs.py`](tests/test_dialogs.py) проверяет и разрешённое,
и закрытое, включая похожие на свои идентификаторы.

## Соединение — [`session.py`](backend/session.py)

Разбирает кадры одного сокета. Хранит, кто на том конце (`self._me`),
и до `HELLO` не пропускает ничего, кроме `PING`.

`HELLO` — вход в сессию. Клиент присылает токен и курсоры по известным ему
документам, сервер отвечает `READY` (кто я, кого видно) и досылает
недостающее. Журнал состава подписывается всегда, даже если клиент
о нём не спросил: без него не из чего строить список людей.
Заканчивается досыл кадром `SYNCED` с головами документов.

Если разрыв больше окна `GAP_LIMIT = 1000`, вместо тысяч записей уходит `RESET` —
клиент пересобирает журнал документа с нуля.

`PING` служит и живостью, и сверкой. Клиент присылает `idx` открытого диалога
и `ts` последнего общего действия; расхождение — сервер досылает пропущенное
прямо в ответ, не дожидаясь переподключения.

Числа из клиентских полей проходят через `_num()`, а не через голый `int()`.
Мусор даёт значение по умолчанию вместо падения — иначе один сломанный клиент
рвёт себе соединение на ровном месте.

## Доставка — [`hub.py`](backend/hub.py)

Реестр живых сокетов, адресуемых по пользователю: `dict[user_id, set[socket]]`.
Набор, а не один сокет, потому что вкладок бывает несколько и все они равноправны.

Мёртвые сокеты отсеиваются молча при первой неудачной отправке — пропущенное
они доберут по `HELLO` при переподключении.

## Кадры — [`protocol.py`](backend/protocol.py)

Конструкторы кадров, по одному на тип. Кадр — объект с полем `t`.
Клиент шлёт `HELLO`, `TX`, `FETCH`, `PING`; сервер отвечает `READY`, `SYNCED`,
`ACK`, `NACK`, `EVT`, `RESET`, `PONG`.

У `NACK` есть флаг `fatal`: отвергнута сессия целиком или только транзакция.
Клиент выкидывает человека на страницу входа только по `fatal`, иначе мусорный
кадр вышибал бы из чата.

Список типов продублирован в [`protocol.js`](frontend/protocol.js) —
их синхронность проверяется тестом.

# Клиент

Голый JavaScript, ES-модули, без сборки и без фреймворка. Браузер грузит модули
как есть. Единственная зависимость — сам браузер.

Ссылки на скрипты помечены версией (`?v=5`). При изменении клиента версия
поднимается, и браузер забирает свежие файлы вместо кешированных.

## Страница входа — [`index.html`](frontend/index.html) + [`auth.js`](frontend/auth.js)

Только форма и `fetch` на `/api/*`. Ни сокета, ни IndexedDB.
Получив токен, уходит на `/chat` через `location.assign`.

Форма видна сразу из разметки, без участия JS. Раньше её открывал скрипт
в самом конце — любой сбой в цепочке импортов оставлял кнопку, на которую
ничего не навешано.

## Сессия — [`session.js`](frontend/session.js)

Токен живёт в `sessionStorage` — у каждой вкладки свой. Сервер не считает
токены одного человека конкурентами, поэтому все вкладки работают
одновременно и на равных: read-only нет ни у одной.

Чтобы новая вкладка не требовала повторного входа, последний вход дублируется
в `localStorage`. Оттуда вкладка берёт токен один раз при открытии и дальше
держит свою копию — логаут в одной не роняет соседние на середине набранного
сообщения.

## Транспорт — [`connection.js`](frontend/connection.js)

Обёртка над `WebSocket`. О содержимом транзакций не знает, только доставляет кадры.

Переподключение с нарастающей паузой: от 500 мс до 15 секунд, с разбросом,
чтобы соединения не ломились обратно одной волной. Раз в 30 секунд уходит `PING`
с курсорами.

Неподтверждённое повторяется только после `SYNCED`. Иначе новая транзакция
получила бы номер раньше, чем клиент дочитал старое.

## Состояние — [`store.js`](frontend/store.js)

Два разных хранилища с разными правилами:

| | ключ | кто пишет | где |
|---|---|---|---|
| подтверждённое | `idx` | только `ACK` и `EVT` | IndexedDB |
| неподтверждённое | `txid` | клиент при отправке | память |

В памяти держится окно текущего документа, остальное остаётся в базе
и поднимается диапазонным запросом при прокрутке вверх.

Записи журнала состава разбираются отдельно: они меняют список людей,
а не ленту сообщений. Разбор идемпотентен — повторно пришедшая запись
ничего не ломает.

## Локальная база — [`storage.js`](frontend/storage.js)

**IndexedDB** — встроенная в браузер база, асинхронная и с индексами
(в отличие от `localStorage`, где только строки и синхронный доступ).

Ключ записи — составной, `[doc, idx]`. Это даёт диапазонные запросы внутри
документа: и досыл вперёд, и окно истории вверх — обход курсором,
без чтения всего журнала. Размер журнала на стоимость выборки не влияет.

Имя базы — `mesera:<user_id>`. Своя на пользователя: в одном браузере могут
работать разные люди, и их журналы не должны попадать в одно хранилище.
Открыть базу без идентификатора нельзя.

## Экран — [`chat.html`](frontend/chat.html) + [`app.js`](frontend/app.js)

Собирает всё вместе и рисует. Отрисовка полная, без виртуального DOM:
`replaceChildren` заменяет содержимое ленты целиком. При окне в тысячу записей
этого достаточно.

Подтверждённые сообщения идут в порядке номеров, неподтверждённые — ниже,
номера у них ещё нет. При догрузке вверх позиция прокрутки удерживается,
иначе экран прыгал бы.

Список людей строится из журнала состава, а не из разового снимка `READY`.
Поэтому новый человек появляется в сайдбаре сам, без перезагрузки.

# Развёртывание

[`Dockerfile`](Dockerfile) — python:3.13-slim, зависимости отдельным слоем
(правки кода не пересобирают `pip install`), непривилегированный пользователь.

[`compose.yaml`](compose.yaml) — наружу порт 80, внутри контейнера приложение
слушает 8100. База лежит на именованном томе и переживает пересборку образа.
`restart: unless-stopped` поднимает контейнер после перезагрузки машины.

```
docker compose up -d --build
```

Локально без Docker — [`run.bat`](run.bat), порт 8100 с автоперезагрузкой.

# Тесты

11 модулей, 105 тестов, каталог [`tests/`](tests/). Запуск:

```
python tests/run_tests.py
```

Каждый модуль исполняется своим процессом: тесты подменяют объект приложения,
и общий интерпретатор дал бы им влиять друг на друга. Тесты клиента идут
через `node` и пропускаются, если его нет.

Фреймворка нет — обычные `assert` и `__main__`. Для проекта такого размера
этого хватает, а зависимость не нужна.

| Модуль | Что проверяет |
|---|---|
| [`test_db.py`](tests/test_db.py) | нумерация, дедупликация, окна, гонка на 20 потоках |
| [`test_users.py`](tests/test_users.py) | scrypt, соли, коллизии логинов, сессии |
| [`test_dialogs.py`](tests/test_dialogs.py) | идентификаторы пар, права доступа |
| [`test_hub.py`](tests/test_hub.py) | доставка по вкладкам, отсев мёртвых сокетов |
| [`test_chat.py`](tests/test_chat.py) | переписка, изоляция чужих диалогов, история |
| [`test_multitab.py`](tests/test_multitab.py) | несколько вкладок пишут одновременно |
| [`test_robust.py`](tests/test_robust.py) | мусорные кадры не рвут соединение |
| [`test_auth.py`](tests/test_auth.py) | разделение страниц и эндпоинтов |
| [`test_users_live.py`](tests/test_users_live.py) | живая рассылка состава |
| [`test_frontend.mjs`](tests/test_frontend.mjs) | состояние клиента на фейковом хранилище |
| [`test_storage.mjs`](tests/test_storage.mjs) | база на пользователя |

Клиентские тесты подменяют `indexedDB`, `localStorage` и `sessionStorage`
заглушками, поэтому идут в Node без браузера.

# Что не сделано

Осознанные пропуски, не забытое:

- **Токен не истекает.** Логаут чистит его у клиента, но серверная запись
  остаётся рабочей. Нужны `/api/logout` и срок жизни.
- **HTTP без шифрования.** Пароли идут открытым текстом. До реальных людей —
  nginx с сертификатом и переезд на 443.
- **Удаление пользователей.** Разбор `user.remove` на клиенте есть,
  серверной ручки нет.
- **Вложения и группы.** Модель документов их допускает, кода нет.
