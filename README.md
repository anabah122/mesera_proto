# mesera_proto

Прототип мессенджера на транзакционном WebSocket. Сервер на Python держит журналы
и раздаёт транзакции, клиент в браузере хранит копию журналов и рисует по ней экран.

Ссылки ведут в конкретные строки файлов — можно сразу открыть нужное место.

- [Запуск](#запуск) · [Общая картина](#общая-картина) · [Путь сообщения](#путь-сообщения)
- [Сервер](#сервер) · [Клиент](#клиент) · [Протокол](#протокол)
- [Тесты](#тесты) · [Развёртывание](#развёртывание) · [Что не сделано](#что-не-сделано)

Причины решений — в [DECISIONS.md](DECISIONS.md). Формат кадров —
в [docs/protocol.html](docs/protocol.html).

## Запуск

Локально:

```
run.bat
```

http://127.0.0.1:8100

В Docker:

```
docker compose up -d --build
```

http://localhost — наружу отдаётся стандартный 80-й порт.

Тесты:

```
python tests/run_tests.py
```

| Доставка | [`backend/hub.py`](backend/hub.py) | реестр живых сокетов |

## Путь сообщения

Полезно проследить целиком — дальше каждый узел понятнее.

1. Человек жмёт «Отправить». [`app.js` зовёт `conn.send()`](frontend/app.js#L119-L125).
2. [`connection.js:35`](frontend/connection.js#L35-L39) заводит `txid`, кладёт транзакцию
   в неподтверждённые и шлёт кадр `TX`. На экране сообщение появляется сразу,
   с пометкой «отправка…».
3. [`session.py:130`](backend/session.py#L130-L150) проверяет права и зовёт `db.append()`.
4. [`db.py:78`](backend/db.py#L78-L107) в одной SQL-транзакции выдаёт следующий `idx`
   и вставляет запись.
5. Автору уходит `ACK` с номером, собеседнику и другим вкладкам — `EVT`
   через [`hub.send_to()`](backend/hub.py#L25-L38).
6. [`store.commit()`](frontend/store.js#L79-L102) переносит транзакцию
   из неподтверждённых в подтверждённые, пишет в IndexedDB и перерисовывает экран.

**Клиент никогда не пишет в свой журнал сам.** Запись появляется там,
только вернувшись с сервера с присвоенным номером.

# Сервер

Python 3.13, **FastAPI** поверх **uvicorn**, **SQLite**. Внешних зависимостей две —
[`requirements.txt`](backend/requirements.txt), обе с зафиксированными версиями.

## Точка входа — [`main.py`](backend/main.py)

Собирает приложение и держит три общих объекта: `db`, `users`, `hub`.

**FastAPI** — веб-фреймворк на ASGI: маршрутизация, разбор JSON, проверка входных
данных через **Pydantic**. Класс [`Credentials`](backend/main.py#L36-L39) описывает
тело запроса, и запрос без нужных полей отсекается до попадания в код.

**uvicorn** — ASGI-сервер, который это исполняет. Модификатор `[standard]`
подтягивает `websockets` и `uvloop`; без него WebSocket работать не будет.

| Маршрут | Строка | Что делает |
|---|---|---|
| `POST /api/register` | [main.py:42](backend/main.py#L42-L53) | заводит человека, отдаёт токен, рассылает `user.add` |
| `POST /api/login` | [main.py:55](backend/main.py#L55-L62) | проверяет пароль, отдаёт новый токен |
| `POST /api/upload` | [main.py:64](backend/main.py#L64-L73) | приём вложения, отдаёт его идентификатор |
| `GET /api/file/{id}` | [main.py:76](backend/main.py#L76-L83) | отдача вложения |
| `GET /` | [main.py:64](backend/main.py#L64-L68) | страница входа |
| `GET /chat` | [main.py:70](backend/main.py#L70-L74) | страница чата |
| `WS /ws` | [main.py:82](backend/main.py#L82-L103) | всё остальное |

Страницы отдаются с [`cache-control: no-cache`](backend/main.py#L76-L80). Иначе браузер
держит старую разметку и не видит обновлённых ссылок на скрипты — на этом легко
потерять час, правя код, который в браузер не доезжает.

[Цикл сокета](backend/main.py#L86-L99) читает кадр как текст и разбирает JSON сам,
а не через `receive_json()`. Так кривой кадр отвечает `NACK` вместо разрыва соединения.

Путь к базе берётся из [`MESERA_DB`](backend/main.py#L22): в контейнере это том,
локально — файл рядом с кодом.

## Журналы — [`db.py`](backend/db.py)

Хранилище документов поверх **SQLite** — модуль `sqlite3` из стандартной библиотеки,
без ORM. [Схема](backend/db.py#L17-L54): таблицы `users`, `sessions`, `doc_head`, `entries`.

Документ — логическая единица со своим журналом. Записи лежат построчно
с составным ключом `(doc, idx)`. Добавление записи не переписывает документ целиком,
поэтому размер журнала не влияет на стоимость операции.

[`append()`](backend/db.py#L78-L107) — единственный путь записи. Номер выдаёт таблица
`doc_head` одним `UPDATE ... RETURNING`, без сканирования журнала. Выдача номера
и вставка идут в одной транзакции, поэтому параллельные вызовы не могут получить
одинаковый `idx`. Повторная отправка той же транзакции возвращает исходную запись:
`txid` уникален в пределах документа — это спасает при переподключении, когда клиент
досылает неподтверждённое.

Выборки: [`entries_after()`](backend/db.py#L127-L134) для досыла вперёд,
[`entries_before()`](backend/db.py#L136-L143) для окна истории вверх,
[`tail()`](backend/db.py#L145-L152) для стартового окна.

**Про блокировку.** [`threading.Lock`](backend/db.py#L59-L65) на каждый доступ.
Соединение одно на всё приложение и делится между потоками — синхронные обработчики
FastAPI выполняются в пуле, а `sqlite3` такие вызовы не сериализует, курсоры затирают
друг друга. Без блокировки параллельная запись роняет `InterfaceError` и теряет номера;
[тест на 20 потоках](tests/test_db.py#L104-L118) это ловит.

Режим журнала — WAL: чтение не блокирует запись.

## Пользователи — [`users.py`](backend/users.py)

Пароль хранится как **scrypt**-хэш ([`_derive()`](backend/users.py#L21-L22),
`hashlib.scrypt` из стандартной библиотеки) со своей солью на каждого.
[Параметры](backend/users.py#L18) `N=2^14, r=8, p=1`. Scrypt требователен к памяти,
что делает перебор на видеокартах дорогим.

[`login()`](backend/users.py#L63-L74) сравнивает через `hmac.compare_digest` —
постоянное время, без утечки по длине совпадения. Когда пользователя нет, хэш всё равно
считается от фиктивной соли: иначе по времени ответа можно было бы перебирать логины.
Текст ошибки одинаков для неверного пароля и несуществующего логина.

[`open_session()`](backend/users.py#L101-L108) выдаёт токен `secrets.token_urlsafe(24)`.
На пользователя их сколько угодно: каждая вкладка получает свой, и они не вытесняют
друг друга. [`by_token()`](backend/users.py#L110-L115) разрешает токен обратно в человека.

[`log_add()`](backend/users.py#L76-L89) кладёт появление человека в журнал состава.
`txid` детерминирован (`user.add:<id>`), поэтому повторный вызов не заводит вторую
запись. [`backfill()`](backend/users.py#L91-L99) при старте достраивает записи для тех,
кто был заведён до появления журнала.

Наружу уходит только [`_public()`](backend/users.py#L127-L135) — документ без соли и хэша.

## Вложения — [`files.py`](backend/files.py)

Картинка не помещается в журнал: base64 раздувает её на треть, а `hub` рассылает
кадр целиком всем вкладкам — один снимок забил бы канал, за которым стоят живые
сообщения. Поэтому тело идёт мимо сокета: файл заливается по HTTP, а в транзакцию
`msg.image` попадает только идентификатор.

Сжатие делает браузер ([`image.js`](frontend/image.js)): длинная сторона до 1600px,
WebP с качеством 0.75, откат на JPEG для старых браузеров. Фото с телефона
из четырёх мегабайт превращается в пару сотен килобайт. Сервер кодировщик
не держит — `Pillow` в зависимости не попал.

[Имя файла](backend/files.py#L48-L50) — случайные 32 символа, поэтому скачивание
прав не проверяет: угадать нельзя, а токен в каждом `<img>` стоил бы дорого.
[`path()`](backend/files.py#L52-L61) отсекает попытки выйти за каталог —
идентификатор приходит из URL.

## Права — [`dialogs.py`](backend/dialogs.py)

[`dialog_id()`](backend/dialogs.py#L12-L14) собирает идентификатор из двух
идентификаторов, отсортированных лексикографически: `d:u_aaa:u_bbb`. Пара всегда даёт
один и тот же результат, кто бы ни писал первым, поэтому отдельной записи о создании
диалога не нужно — первая транзакция и есть его начало.

Два предиката решают всё:

- [`can_read()`](backend/dialogs.py#L26-L28) — состав системы виден всем,
  диалог только его паре;
- [`can_write()`](backend/dialogs.py#L31-L33) — в журнал состава пишет только сервер,
  диалог только его паре.

Это единственная преграда между чужой перепиской и клиентом, поэтому
[`test_dialogs.py`](tests/test_dialogs.py) проверяет и разрешённое, и закрытое,
включая похожие на свои идентификаторы.

## Соединение — [`session.py`](backend/session.py)

Разбирает кадры одного сокета. [`handle()`](backend/session.py#L39-L52) хранит,
кто на том конце, и до `HELLO` не пропускает ничего, кроме `PING`.

[`_on_hello()`](backend/session.py#L60-L97) — вход в сессию. Клиент присылает токен
и курсоры по известным ему документам, сервер отвечает `READY` (кто я, кого видно)
и досылает недостающее. [Журнал состава](backend/session.py#L74-L77) подписывается
всегда, даже если клиент о нём не спросил: без него не из чего строить список людей.
Заканчивается досыл кадром `SYNCED` с головами документов.

Если разрыв больше окна [`GAP_LIMIT = 1000`](backend/session.py#L15), вместо тысяч
записей уходит `RESET` — клиент пересобирает журнал документа с нуля.

[`_on_ping()`](backend/session.py#L99-L128) служит и живостью, и сверкой. Клиент
присылает `idx` открытого диалога и `ts` последнего общего действия; расхождение —
сервер досылает пропущенное прямо в ответ, не дожидаясь переподключения.

Числа из клиентских полей проходят через [`_num()`](backend/session.py#L18-L23),
а не через голый `int()`. Мусор даёт значение по умолчанию вместо падения — иначе
один сломанный клиент рвёт себе соединение на ровном месте.

## Доставка — [`hub.py`](backend/hub.py)

[Реестр](backend/hub.py#L12) живых сокетов, адресуемых по пользователю:
`dict[user_id, set[socket]]`. Набор, а не один сокет, потому что вкладок бывает
несколько и все они равноправны.

[`send_to()`](backend/hub.py#L25-L38) шлёт кадр всем сокетам перечисленных людей,
[`broadcast()`](backend/hub.py#L40-L41) — вообще всем. Мёртвые сокеты отсеиваются
молча при первой неудачной отправке: пропущенное они доберут по `HELLO`
при переподключении.

# Клиент

Голый JavaScript, ES-модули, без сборки и без фреймворка. Браузер грузит модули как есть.
Единственная зависимость — сам браузер.

Ссылки на скрипты помечены версией (`?v=5`). При изменении клиента версия поднимается,
и браузер забирает свежие файлы вместо кешированных.

## Страница входа — [`index.html`](frontend/index.html) + [`auth.js`](frontend/auth.js)

Только форма и `fetch` на `/api/*`. Ни сокета, ни IndexedDB. Получив токен,
[уходит на `/chat`](frontend/auth.js#L32-L48).

Форма видна сразу из разметки, без участия JS. Раньше её открывал скрипт в самом конце —
любой сбой в цепочке импортов оставлял кнопку, на которую ничего не навешано.

## Сессия — [`session.js`](frontend/session.js)

Токен живёт в `sessionStorage` — [у каждой вкладки свой](frontend/session.js#L15-L23).
Сервер не считает токены одного человека конкурентами, поэтому все вкладки работают
одновременно и на равных: read-only нет ни у одной.

Чтобы новая вкладка не требовала повторного входа, последний вход дублируется
в `localStorage`. Оттуда вкладка берёт токен один раз при открытии и дальше держит свою
копию — логаут в одной не роняет соседние на середине набранного сообщения.

## Транспорт — [`connection.js`](frontend/connection.js)

Обёртка над `WebSocket`. О содержимом транзакций не знает, только доставляет кадры.

[`open()`](frontend/connection.js#L26-L33) поднимает сокет,
[`_onFrame()`](frontend/connection.js#L63-L122) разбирает входящие кадры по типу.

[Переподключение](frontend/connection.js#L141-L148) с нарастающей паузой: от 500 мс
до 15 секунд, с разбросом, чтобы соединения не ломились обратно одной волной.
Раз в 30 секунд уходит [`_ping()`](frontend/connection.js#L125-L134) с курсорами.

Неподтверждённое [повторяется только после `SYNCED`](frontend/connection.js#L104-L112).
Иначе новая транзакция получила бы номер раньше, чем клиент дочитал старое.

## Состояние — [`store.js`](frontend/store.js)

Два разных хранилища с разными правилами:

| | ключ | кто пишет | где |
|---|---|---|---|
| подтверждённое | `idx` | только `ACK` и `EVT` | IndexedDB |
| неподтверждённое | `txid` | клиент при отправке | память |

[`addPending()`](frontend/store.js#L61-L64) кладёт транзакцию в неподтверждённые,
[`commit()`](frontend/store.js#L79-L102) переносит её в подтверждённые, когда запись
вернулась с сервера.

В памяти держится окно текущего документа, остальное остаётся в базе и поднимается
[`older()`](frontend/store.js#L104-L117) при прокрутке вверх.

Записи журнала состава разбираются [отдельно](frontend/store.js#L35-L39): они меняют
список людей, а не ленту сообщений. Разбор идемпотентен — повторно пришедшая запись
ничего не ломает. [`loadUsers()`](frontend/store.js#L29-L33) поднимает состав
из прошлого сеанса до подключения.

## Локальная база — [`storage.js`](frontend/storage.js)

**IndexedDB** — встроенная в браузер база, асинхронная и с индексами, в отличие
от `localStorage`, где только строки и синхронный доступ.

Ключ записи — составной, `[doc, idx]`. Это даёт диапазонные запросы внутри документа:
и досыл вперёд, и [окно истории вверх](frontend/storage.js#L60-L78) — обход курсором,
без чтения всего журнала. Размер журнала на стоимость выборки не влияет.

[Имя базы](frontend/storage.js#L26-L34) — `mesera:<user_id>`. Своя на пользователя:
в одном браузере могут работать разные люди, и их журналы не должны попадать в одно
хранилище. Открыть базу без идентификатора нельзя.

## Экран — [`chat.html`](frontend/chat.html) + [`app.js`](frontend/app.js)

Собирает всё вместе и рисует. [`start()`](frontend/app.js#L41-L61) открывает базу
пользователя, поднимает состав и подключает сокет.

[Отрисовка](frontend/app.js#L161-L189) полная, без виртуального DOM: `replaceChildren`
заменяет содержимое ленты целиком. При окне в тысячу записей этого достаточно.
Подтверждённые сообщения идут в порядке номеров, неподтверждённые — ниже, номера у них
ещё нет. При догрузке вверх позиция прокрутки удерживается, иначе экран прыгал бы.

Список людей строится [из журнала состава](frontend/app.js#L87-L90), а не из разового
снимка `READY`. Поэтому новый человек появляется в сайдбаре сам, без перезагрузки.

# Протокол

Кадр — объект с полем `t`. Конструкторы: [`backend/protocol.py`](backend/protocol.py),
типы продублированы в [`frontend/protocol.js`](frontend/protocol.js) —
их синхронность [проверяется тестом](tests/test_frontend.mjs).

| Кадр | Направление | Смысл |
|---|---|---|
| `HELLO` | клиент → сервер | токен и курсоры, вход в сессию |
| `TX` | клиент → сервер | транзакция на запись |
| `FETCH` | клиент → сервер | добор окна истории |
| `PING` | клиент → сервер | живость и сверка курсоров |
| `READY` | сервер → клиент | кто я и кого видно |
| `SYNCED` | сервер → клиент | досыл окончен, головы документов |
| `ACK` | сервер → клиент | транзакция принята, вот её номер |
| `NACK` | сервер → клиент | отказ |
| `EVT` | сервер → клиент | запись журнала |
| `RESET` | сервер → клиент | журнал документа пересобрать с нуля |
| `PONG` | сервер → клиент | живость и серверное время |

У [`nack()`](backend/protocol.py#L36-L38) есть флаг `fatal`: отвергнута сессия целиком
или только транзакция. Клиент выкидывает человека на страницу входа
[только по `fatal`](frontend/connection.js#L86-L95), иначе мусорный кадр вышибал бы
из чата.

Подробная спецификация — [docs/protocol.html](docs/protocol.html).

# Развёртывание

[`Dockerfile`](Dockerfile) — python:3.13-slim, зависимости отдельным слоем
(правки кода не пересобирают `pip install`), непривилегированный пользователь.

[`compose.yaml`](compose.yaml) — наружу порт 80, внутри контейнера приложение слушает
8100. База лежит на именованном томе и переживает пересборку образа.
`restart: unless-stopped` поднимает контейнер после перезагрузки машины.

```
docker compose up -d --build
```

Локально без Docker — [`run.bat`](run.bat), порт 8100 с автоперезагрузкой.

**Переменные:** `MESERA_DB` — путь к базе, `MESERA_FILES` — каталог вложений.
В контейнере оба на томе, локально рядом с кодом.

# Что не сделано

Осознанные пропуски, не забытое:

- **Токен не истекает.** Логаут чистит его у клиента, но серверная запись остаётся
  рабочей. Нужны `/api/logout` и срок жизни.
- **HTTP без шифрования.** Пароли идут открытым текстом. До реальных людей —
  nginx с сертификатом и переезд на 443.
- **Удаление пользователей.** Разбор `user.remove`
  [на клиенте есть](frontend/store.js#L35-L39), серверной ручки нет.
- **Вложения и группы.** Модель документов их допускает, кода нет.
